# Интеграция фронтенда и бэкенда ThroughTheLense

Дневник собирает сцену в браузере. Бэкенд отвечает за вход и хранение готовых дней. Редактор, архив и плеер используют интерфейс `web/diary.mjs`. Тот же HTTP API реализуют локальный Python-сервер и Go-сервер из `backend/`.

## Go-сервер

Каталог `backend/` содержит Go-сервер, который заменяет `account_server.py` и `serve.py` при развёртывании. Он реализует [локальный HTTP API](#локальный-http-api) байт в байт: те же маршруты, тела, тексты ошибок, cookie `ttl_session`, проверку `X-Diary-Request` и `Origin` до разбора маршрута, лимиты 76 МиБ и 360 000 символов и `429` с `Retry-After: 60`. Поэтому `web/account.mjs` и `web/diary.mjs` не меняются, а `tests/experience.cjs` проверяет оба сервера.

| Отличие от Python | Причина |
| --- | --- |
| Пароли хешируются argon2id (19 МиБ, 2 прохода), сессии хранятся как sha256 токена | Тот же формат cookie, более стойкий хеш |
| Копия дня лежит файлом `DATA_DIR/copies/<revision>.json`. Сводка и ревизия меняются в SQLite одной операцией. Файл записывается во временный, синхронизируется и переименовывается до записи строки | Читатель никогда не видит частичную копию. Ежечасная очистка удаляет временные и неиспользуемые файлы |
| При сохранении сервер дополнительно проверяет 1–5 фото и размеры base64 так же, как `importDay` в `web/transfer.mjs` | Сервер не принимает копию, которую браузер не сможет открыть |
| С `PUBLIC_BASE_URL` проверка `Host` и `Origin` идёт по этому адресу, cookie получает `Secure`. С `TRUST_PROXY=1` лимиты считаются по последнему адресу `X-Forwarded-For`. `GET /api/runtime` отвечает при любом `Host`, чтобы проходила проверка здоровья платформы | Развёртывание за прокси вместо работы только на `127.0.0.1` |
| `robots.txt` и `sitemap.xml` строятся по `PUBLIC_BASE_URL` или `http://127.0.0.1:PORT` | Как у `serve.py`, независимо от `SITE_ORIGIN` сборки |

`Dockerfile` собирает `dist/` командой `npm run build` с `SITE_ORIGIN`, затем статический Go-бинарь, и задаёт `WEB_DIR=/app/dist` и `DATA_DIR=/data`. Том монтируется в `/data`. SQLite рассчитана на один экземпляр сервиса.

### Публичные ссылки (только Go)

| Метод и путь | Доступ | Ответ |
| --- | --- | --- |
| `GET /api/days/:id/share` | Владелец | `{ "slug": "…", "url": "…/d/…" }` или `{ "slug": null, "url": null }` |
| `POST /api/days/:id/share` | Владелец, `X-Diary-Request` | Та же пара. Повторный вызов возвращает прежнюю ссылку. `404` для чужого или отсутствующего дня, `422` «Этот день нельзя опубликовать. …», если копия не прошла строгую проверку |
| `DELETE /api/days/:id/share` | Владелец, `X-Diary-Request` | `{ "ok": true }`. Ссылка сразу перестаёт работать |
| `GET /api/public/:slug` | Все | JSON-копия дня, как `GET /api/days/:id`, с `X-Robots-Tag: noindex`. Отозванная или неизвестная ссылка: `404` «Ссылка не найдена или отозвана.» |
| `GET /api/public/:slug/cover` | Все | Обложка из сводки (`image/jpeg`, `png` или `webp`) для превью в соцсетях |
| `GET /d/:slug` | Все | `shared.html` из `WEB_DIR` с `og:`-метатегами и `noindex`. Без `shared.html` или для недействительной ссылки отдаётся `404.html` |

Go добавляет в ответ `GET /api/runtime` поле `"share": true`, но только в режиме `local`. Python-сервер, Vercel и режим Supabase это поле не отдают. По флагу фронтенд решает, показывать ли «Поделиться».

Slug состоит из 22 символов base64url (128 случайных бит). Ответы не содержат почту, `id` пользователя и `id` дня. Строгая проверка (`backend/internal/copycheck`) выполняется при публикации и перед каждой отдачей новой ревизии. Тип фото и трека определяется по байтам, не по имени: JPEG/PNG/WebP до 8 МиБ, WAV/MP3 до 12 МиБ длительностью 3–60 секунд. Объявленный тип должен совпадать с содержимым, фраза должна быть взята из текста. Если день отредактировали в непроходящую копию, ссылка отвечает `404`, пока владелец не сохранит исправленную версию. Удаление дня удаляет ссылку.

### Деплой на Railway

Go-сервер развёрнут на <https://throughthelense-production.up.railway.app>: проект и сервис `throughthelense`, окружение `production`. Railway собирает `Dockerfile` (`railway.toml`: сборщик `DOCKERFILE`, проверка `/api/runtime`, перезапуск `ON_FAILURE`). Том смонтирован в `/data`. В нём лежат `journal.sqlite` и каталог `copies/`, и они переживают `railway redeploy`. При первом старте сервер сам создаёт пустую базу.

| Особенность Railway | Как учтено |
| --- | --- |
| Проверка здоровья приходит с `Host: healthcheck.railway.app` | `GET /api/runtime` отвечает при любом `Host`. Остальные `/api/*` требуют `PUBLIC_BASE_URL` |
| Переменные сервиса попадают в сборку только через `ARG` | `ARG SITE_ORIGIN` в стадии сборки `dist/` |
| Том монтируется с владельцем root, инструкция `VOLUME` не поддерживается | Финальный образ `distroless/static` от root, без `VOLUME` |
| Прокси добавляет адрес клиента в конец `X-Forwarded-For` | С `TRUST_PROXY=1` лимиты попыток считаются по последнему адресу. Более ранние адреса присылает клиент |
| Edge маршрутизирует по `Host` | Запрос с чужим `Host` получает 404 от Railway и не доходит до приложения |

Передеплой: `railway up --ci` из корня проекта. Перезапуск без новой сборки: `railway redeploy -y`. SQLite рассчитана на один экземпляр, поэтому реплики не добавляйте. `railway.toml` работает до 01.12.2026, после этой даты Railway предлагает перейти на `railway config migrate`.

## Хранение и выбор режима

| Как открыт дневник | Готовые записи | Черновики |
| --- | --- | --- |
| Без сессии, без настроенного входа или по `/journal.html?mode=guest#archive` | IndexedDB `ThroughTheLense` в профиле браузера | Там же, в `drafts` |
| Локальный аккаунт | SQLite `.ttl-data/journal.sqlite` на компьютере, где запущен `serve.py` | IndexedDB `ThroughTheLense-local-{userId}` |
| Аккаунт Supabase | Метаданные в Postgres, материалы в закрытом бакете Storage | IndexedDB `ThroughTheLense-supabase-{userId}` |

Если при старте не удалось определить сессию, дневник показывает сообщение и открывает гостевой режим. Ошибка чтения или сохранения уже подключённого аккаунта показывается в интерфейсе. Такой день не записывается в гостевое хранилище вместо аккаунта.

Раздел «Мои дни» на главной читает только гостевую IndexedDB. Вход не переносит гостевые дни и черновики в аккаунт. Чтобы перенести готовый день, скачайте его копию в гостевом архиве, войдите и откройте файл в архиве аккаунта. Импорт создаёт отдельную запись с новым идентификатором. Публичные примеры из [`web/demo.mjs`](../web/demo.mjs) доступны без входа и не входят в списки API.

## Контракт записей

При сохранении фронтенд передаёт адаптеру `save(id, summary, copy, editing)`. Адаптер возвращает через `list()` массив сводок с `id`, через `open(id)` — JSON-копию как `Blob` или `undefined` для отсутствующего дня, через `remove(id)` — результат операции удаления. `save` и `remove` должны отклонять промис при ошибке, чтобы интерфейс не сообщал об успешном сохранении или удалении раньше времени.

- `id` создаёт браузер. Обычно это UUID. Текущие серверы принимают от 8 до 64 символов из `[A-Za-z0-9_-]`. Дата и заголовок могут повторяться. Ключ записи состоит из владельца и `id`.
- `summary` содержит `dayDate` (`YYYY-MM-DD`), `title`, `audioName`, `photoCount`, `thumbnail` и `duration` в секундах. Обложка передаётся как `data:image/jpeg;base64,…`. Клиент также читает обложки с типом PNG или WebP. Сводка сохраняется без `id`, при чтении списка адаптер добавляет его из ключа. Фронтенд сортирует и фильтрует список сам.
- `copy` — полные данные дня. Для HTTP это вложенный JSON-объект в запросе записи и тело ответа при чтении. Для Supabase это JSON-файл, разбитый на части. Локальный экспорт использует тот же формат.
- `editing` равен `true` при сохранении существующего дня. Если день уже удалён, адаптер сообщает об ошибке. Повторное создание с тем же идентификатором не должно перезаписывать существующий день. Храните сводку и содержимое одной согласованной версии. При неудачном сохранении пользователь может повторить попытку из предпросмотра.

В браузерной записи `entry` материалы представлены как `photoFiles: File[]` и `audioFile: File`. Объект `scene` содержит `version`, `coverPhotoIndex`, `quote`, `palette`, `quoteAtSec`, `returnAtSec` и `endAtSec`. `transfer.mjs` преобразует эту модель в JSON и обратно. Черновик нового дня хранится под ключом `new`, а черновик редактирования — под `id` дня. При открытии записи фронтенд создаёт временные `blob:` URL и передаёт их плееру. Эти адреса живут только в браузере.

Структура `copy` версии 1. Значения `data` ниже обозначают base64 фактических файлов.

```json
{
  "format": "ThroughTheLense/day",
  "version": 1,
  "dayDate": "2026-11-17",
  "title": "Прогулка после дождя",
  "text": "Уже стемнело. Мы вышли на улицу после дождя.",
  "audioName": "Вечерний маршрут",
  "quote": "Мы вышли на улицу после дождя.",
  "coverIndex": 0,
  "photos": [{"name": "cover.jpg", "type": "image/jpeg", "data": "<base64 JPEG>"}],
  "audio": {"name": "track.wav", "type": "audio/wav", "data": "<base64 WAV>"},
  "cues": {"quoteAtSec": 2.7, "returnAtSec": 7.8}
}
```

Допустимы 1–5 фото JPEG, PNG или WebP до 8 МиБ каждое, один MP3 или WAV от 3 до 60 секунд до 12 МиБ, название до 120 символов и дословная фраза из `text` до 200 символов. `coverIndex` начинается с нуля. Метки идут по порядку от появления фразы до возврата кадра и должны помещаться в сцену. Сцена длится не более 12 секунд. При открытии JSON фронтенд декодирует файлы, вычисляет палитру, миниатюру и длительность и сохраняет указанные метки, если они допустимы. Просмотр использует исходное фото, звук и текст в браузерном плеере. Отдельный видеофайл серверу не требуется.

## Локальный HTTP API

Запросы идут на тот же origin. Текущий клиент `web/account.mjs` отправляет `X-Diary-Request: 1`. Локальный сервер требует этот заголовок для изменений и проверяет `Origin`, если он присутствует. Сессия передаётся cookie `ttl_session` с `Path=/api`, `HttpOnly`, `SameSite=Strict` и сроком 14 дней. Сервер сам получает владельца по сессии. Ошибки API возвращаются как `{ "message": "…" }` с HTTP-статусом.

| Метод и путь | Данные запроса | Успешный ответ |
| --- | --- | --- |
| `GET /api/runtime` | — | `{ "mode": "local", "analytics": "local" }` по умолчанию |
| `GET /api/session` | Cookie при наличии | `{ "user": { "id": "…", "email": "…" } }` или `{ "user": null }` |
| `POST /api/register`, `POST /api/login` | `{ "email": "…", "password": "…" }` | `{ "user": { "id": "…", "email": "…" } }` и `Set-Cookie` |
| `POST /api/logout` | Cookie при наличии | `{ "ok": true }` и очистка cookie |
| `GET /api/days` | Сессия | `{ "days": [...] }`, включая `id` каждой записи |
| `GET /api/days/:id` | Сессия | JSON-копия дня целиком, без внешнего ключа `copy` |
| `PUT /api/days/:id` | Сессия и `{ "summary": { … }, "copy": { … }, "editing": false }` | `{ "ok": true }` |
| `DELETE /api/days/:id` | Сессия | `{ "ok": true }`, включая повторное удаление отсутствующего у владельца дня |

Запросы архива без сессии получают `401`. Чтение дня по идентификатору, которого у владельца нет, возвращает `404`. Дубликат адреса при регистрации даёт `409`, неверный пароль — `401`, запрос сверх лимита — `413`. Локальный сервер принимает до 76 МиБ на `PUT` вместе с JSON-обёрткой и ограничивает сериализованную сводку 360 000 символами. Лимиты попыток регистрации и входа действуют на весь локальный процесс в пределах одной минуты. При превышении возвращается `429` и `Retry-After: 60`.

Локальная аналитика отделена от дневника. После согласия браузер отправляет `POST /api/analytics` с `{ "event": "home_view" }` без cookie. SQLite увеличивает общий счётчик посещений за день. Содержимое дневника и адрес почты в этом запросе отсутствуют. [`web/consent.mjs`](../web/consent.mjs)

## Supabase и другой бэкенд

На Vercel `GET /api/runtime` возвращает либо `{ "mode": "supabase", "url": "…", "key": "…" }`, либо `{ "mode": "guest" }` при отсутствии конфигурации. В режиме Supabase браузер вызывает Auth и Storage через SDK. Локальные REST-маршруты из таблицы выше Vercel не разворачивает. `npm run build` собирает статику в `dist` и копирует туда SDK. [`api/runtime.mjs`](../api/runtime.mjs) · [`scripts/build.mjs`](../scripts/build.mjs)

1. Примените [миграцию](../supabase/migrations/20261120202922_diary_storage.sql) к тестовому проекту. Она создаёт `diary_days` с ключом `(owner, id)` и закрытый бакет `diary-copies`. Политики RLS сверяют владельца строки и первый сегмент пути объекта с `auth.uid()`.
2. Укажите `SUPABASE_URL` и `SUPABASE_PUBLISHABLE_KEY` в окружении, в котором запускается сервер конфигурации. В браузер возвращается только ключ формата `sb_publishable_…`. Для Vercel доступны также имена с префиксом `NEXT_PUBLIC_`. Серверные ключи, токены, дампы базы и медиа личных записей держите вне клиентских файлов и репозитория.
3. В Auth укажите адрес сайта и разрешите возврат на `/account.html`. Если подтверждение почты включено, после регистрации без сессии интерфейс предлагает проверить почту. Адрес и пересылка писем настраиваются в Supabase, сценарий входа проверяется в тестовом проекте.

В облачной таблице запись указывает на `revision` и число `parts`. Копия разбивается на части до 4 МиБ, максимум 19. Путь каждой части имеет вид `{owner}/{revision}/{index}.json`. После загрузки всех частей адаптер записывает новую сводку и ревизию, при редактировании сверяет прежнюю ревизию. При сбое и после успешной замены удаление лишних объектов выполняется по возможности. Ограничение `summary` в Postgres составляет 360 000 байт сериализованного JSON. [`web/cloud-diary.mjs`](../web/cloud-diary.mjs)

Если пишете свой сервис, удобнее начать с существующего `localDiary` в [`web/account.mjs`](../web/account.mjs). При сохранении HTTP-контракта редактор менять не нужно. При другом формате ответа преобразуйте его в показанные структуры внутри адаптера. Если переносите вход или меняете схему сессии, менять нужно также `currentUser`, `login`, `logout` и выбор режима в [`web/diary.mjs`](../web/diary.mjs). Изоляцию владельцев обеспечивайте на сервере для всех операций, включая чтение и скачивание медиа по известному адресу. Текущий локальный сервер слушает только `127.0.0.1` и рассчитан на запуск на компьютере участника.

## Проверка перед передачей

Запуск из корня проекта в первом терминале. Временный каталог оставляет рабочую SQLite без изменений.

```sh
npm ci
npm run build:visuals
TTL_DATA_DIR="$(mktemp -d)" python3 serve.py --no-browser --port 8012
```

Откройте [главную в локальной тестовой копии](http://127.0.0.1:8012/). Во втором терминале из корня проекта запустите проверки.

```sh
npx playwright install chromium
npm test
TTL_TEST_URL=http://127.0.0.1:8012 npm run test:experience
```

- [`tests/experience.cjs`](../tests/experience.cjs) проверяет регистрацию, вход и выход, сохранение в аккаунт, повторный вход, изоляцию двух аккаунтов, запросы без сессии и ограничение попыток входа. Он проходит против Python и Go: для Go выполните `npm run build`, запустите `cd backend && WEB_DIR=../dist DATA_DIR="$(mktemp -d)" go run ./cmd/server` и укажите `TTL_TEST_URL=http://127.0.0.1:8080`. Go-тесты: `cd backend && go test ./...`.
- [`tests/browser.cjs`](../tests/browser.cjs) запускается через `npm run test:browser` при сервере на порте `8000`. Он проходит гостевой сценарий, в том числе валидацию, восстановление, ручные метки, повторное сохранение и совместимость со старым форматом IndexedDB.
- Для Supabase или нового сервиса повторите сценарий с двумя тестовыми аккаунтами. Под первым сохраните день, обновите страницу, откройте его после повторного входа и измените метки. Под вторым проверьте пустой список и невозможность открыть или удалить запись первого даже по её `id`. Под первым снова откройте день. Отдельно проверьте импорт скачанной копии и гостевой режим. Прогоны локального API не проверяют политики и доставку писем вашего облачного проекта.
